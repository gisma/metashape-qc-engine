
# User Manual — Metashape QC Engine

## 1. Project Overview & Philosophy

The Metashape QC Engine addresses two complementary quality‑assessment challenges for UAV orthomosaics:

**Pillar A — Orthomosaic Reproducibility Analysis**
The core pipeline repeatedly builds orthomosaics with Metashape under varying parameter configurations (e.g., dense‑cloud quality, smoothing levels). Each replicate is an independent, full photogrammetric reconstruction. The resulting orthomosaics are then aligned on a canonical grid and evaluated with a suite of stability metrics (median‑robust RMSE, MAD, support‑persistence fractions). The goal is not to find the “best” orthomosaic in an absolute sense, but to quantify how stable the product is under repeated processing of the same raw imagery. This information helps decide whether a particular parameter‑set delivers a trustworthy orthomosaic for downstream ecological or surveying work.

**Pillar B — Level‑1b Candidate‑Scale Stability**
Level‑1b is a raster‑based quality step that starts from a finished orthomosaic. It does not produce a final object map. Instead, it systematically explores a range of segmentation scales and their local perturbations to build a Candidate‑Scale Response Surface. The central question is: Do the segment populations generated by the workflow behave stably when the segmentation parameters are slightly changed? Stability is assessed both globally (distribution of segment‑size classes) and spatially (are problematic regions consistent across slight parameter changes?). Level‑1b therefore identifies stable spatial information carriers—plausible segmentation scales and their associated stable response regions. The output is an evidence package, not a classified map.

These two pillars share the same system environment but are independent workflows. The rest of this manual treats them separately.

## 2. Central System Setup & Environment

This section covers the one‑time setup required for both pillars. Perform these steps before using either Part I or Part II.

### 2.1 Python Virtual Environment

The project requires Python ≥ 3.9. From the repository root:

```bash
python3 -m venv venv
source venv/bin/activate
pip install -e .

```

The `-e` (editable) install reads `pyproject.toml` and makes the console script `metashape-qc` available. Core dependencies installed automatically:

* `numpy`
* `PyYAML` (≥6.0)
* `rasterio`

Additional packages needed for Level‑1b (Part II) — install on demand:

```bash
pip install matplotlib gdal

```

*(Installing `gdal` may require that the system GDAL development headers match the version; use `pip install GDAL==$(gdal-config --version)` if necessary.)*

### 2.2 Agisoft Metashape

The reproducibility pipeline shells out to Metashape. The environment variable `METASHAPE_DIR` must point to the Metashape installation directory (the one containing `metashape.sh`):

```bash
export METASHAPE_DIR=/path/to/metashape-pro

```

Verify: `ls $METASHAPE_DIR/metashape.sh` should show a regular executable file.

### 2.3 System Dependencies for Level‑1b

Level‑1b relies on external command‑line tools; they must be on your `PATH`.

| Dependency | Requirement | Verification |
| --- | --- | --- |
| **Orfeo ToolBox** | All `otbcli_*` executables, e.g., `otbcli_BandMathX` | `which otbcli_BandMathX` |
| **GDAL / OGR** | `gdalwarp`, `ogr2ogr`, … | `which gdalwarp` |
| **R** | `Rscript` must be callable | `which Rscript` |
| **R packages** | `exactextractr`, `sf`, `terra`, `jsonlite`, `readr` | `Rscript -e 'library(exactextractr)'` |

Install R packages with:

```R
install.packages(c("exactextractr", "sf", "terra", "jsonlite", "readr"))

```

With this environment in place, you can proceed to either workflow.

## 3. Part I — Orthomosaic Reproducibility Analysis

### 3.1 Quickstart

```bash
# 1. Prepare control files (config + variant table)
metashape-qc prepare \
  --image-dir /data/images \
  --product-id my_product \
  --preset '{"buildDenseCloud": {"quality": "medium"}}' \
  --reps 5 \
  --output-root ./runs/my_product \
  --factor "buildOrthomosaic.orthoRes=0.05,0.10,0.20"

# This creates:
#   ./runs/my_product/config.yml
#   ./runs/my_product/variants.csv

# 2. Run the experiment
metashape-qc run-analysis \
  ./runs/my_product/config.yml \
  --variants ./runs/my_product/variants.csv \
  --reps 5 \
  --run-dir ./runs/my_product

# 3. Evaluate results
metashape-qc evaluate ./runs/my_product

```

### 3.2 Step‑by‑Step Details

**`prepare`**
Generates a base YAML configuration and a CSV variant table. Each column in the variant table (except `variant_id`) corresponds to a dotted key in the YAML; each row is one variant.

| Flag | Description |
| --- | --- |
| `--image-dir DIR` | Path to the original raw images (used to build absolute image paths). |
| `--product-id ID` | Short product identifier. |
| `--preset JSON` | YAML‑compatible JSON snippet merged into the base config. |
| `--reps N` | Number of independent replicate builds per variant. |
| `--output-root DIR` | Destination directory for the generated `config.yml` and `variants.csv`. |
| `--factor COL=VALUES` | Repeatable; builds combinatorial variants for the given column. |
| `--variant-id-template` | Python format string with `{column}` placeholders, e.g., `"id_{quality}"`. |
| `--face-counts VALUES` | Optional override list for `alignPhotos.faceCount` (comma‑separated). |
| `--smoothing VALUES` | Optional override list for `buildModel.smoothing`. |

**`run-analysis` (or `resume-analysis`)**
Executes all variants × replicates. Each replicate is a fresh Metashape project (the `load_project` key is forced to empty).

| Flag | Description |
| --- | --- |
| `BASE_CONFIG` | Path to the generated `config.yml`. |
| `--variants CSV` | Path to `variants.csv`. |
| `--reps N` | Number of replicates per variant (must be ≥ 2 for a reproducibility study). |
| `--run-dir DIR` | Working directory; must be empty or contain only prepared control files. |
| `--generic-ortho-resolution` | Single‑replicate probe with `orthoRes = 0` to determine technical sampling. |
| `--metashape-dir` | Optionally override `METASHAPE_DIR`. |
| `--overwrite` | Allow re‑using a non‑empty run directory. |

`resume-analysis` is identical to `run-analysis` but skips any variant/replicate whose previous status in `manifest.csv` is `ok` or `ok_no_ortho` and whose output files still exist.

**`evaluate`**
Performs the stability analysis and writes human‑readable reports.

| Flag | Description |
| --- | --- |
| `EXPERIMENT_DIR` | The same directory used as `--run-dir`. |
| `--skip-analyzer` | Reuse existing `stability_union/summary.csv` without recomputing rasters. |
| `--grid-mode` | `union`, `intersection`, or `reference` (default: union). |
| `--bands N` | Number of bands to analyse (default 3). |
| `--stable-rmse-threshold X` | RMSE‑to‑median threshold for stable/unstable masks (default 15.0). |
| `--no-overwrite` | Do not pass `--overwrite` to the analyzer. |

### 3.3 Output Artifacts

Inside the run directory:

* `manifest.csv` — one row per variant/replicate with status (`ok`, `ok_no_ortho`, `failed`), return code, output paths, and wall‑clock time.
* `variants/<variant_id>/runs/<rep>/` — per‑replicate Metashape projects, logs, and orthomosaics.
* `variants/<variant_id>/configs/<rep>.yml` — the exact YAML used for that replicate.
* `stability_union/` — after evaluation: aligned orthomosaics, stability rasters (`median_ortho.tif`, `valid_count.tif`, `rmse_to_median.tif`, `mad_rgb.tif`), summary `.csv/.tsv` files, evaluation report (`evaluation_report.md`).
* `selected_product.json` — the automatically chosen “most stable” variant and a recommended medoid replicate, plus support‑persistence context.
* QGIS launcher scripts (`qgis_open_selected.sh`, `.bat`) to visually inspect the selected variant’s layers.

### 3.4 Interpreting the Results

The evaluation report ranks variants by continuous stability (lower `p95_rmse_to_median`, then lower `mean_rmse_to_median`, etc.). A separate support‑persistence ranking (based on the `valid_count` histogram) shows which variant has the largest proportion of pixels consistently covered across replicates. The final selected product uses the continuous stability variant, with support‑persistence as context; a warning is emitted if the two differ.

## 4. Part II — Level‑1b Candidate‑Scale Stability

### 4.1 Conceptual Goal

Level‑1b does not create a final segmented map. Instead, it answers:
*“Within which segmentation parameter ranges does the image produce a stable, scale‑consistent set of segments?”*

A candidate scale (in metres) is translated into pixel‑space parameters (search radius `spatialr`, minimum segment size `minsize`, feature‑space distance `ranger`). A small set of local perturbations around these values is applied, generating a response surface of segment populations. Stability is judged by:

* **Global metrics:** how much the segment‑size distribution shifts between perturbations.
* **Spatial metrics:** whether local problem zones (e.g., very small or very large segments) remain constant or jump between runs.
* **Tail behaviour:** excessive oversize or micro segments.

A stable candidate scale shows a robust segment population that is neither systematically too fine nor too coarse relative to the expected scale, and that resists small parameter changes.

The output is an evidence package: a chosen representative run, its vectorised segments, `exactextractr` stats on the original pixel values, and a quality‑info JSON. These can later be used to guide manual interpretation, but they are not an automatic ecological object map.

### 4.3 Running the Chain

In practice, the Level‑1b workflow is executed using a provided bash wrapper script. This script handles the complex environment setup (sourcing OTB profiles, fixing GDAL paths, setting PYTHONPATH) before launching the underlying Python engine.

Edit the variables at the top of the script or pass them via the environment, then run:

```bash
cd /path/to/metashape-qc-engine
export ORTHO="/data/ortho.tif"
export RUN_ROOT="./level1b_results"
export OVERWRITE="1"  # Set to 1 to overwrite existing results

./run_level1b_dumb_with_user_header.sh

```

**What the wrapper does behind the scenes:**
1. Sources the Orfeo ToolBox environment (`otbenv.profile`).
2. Configures `PATH` and `LD_LIBRARY_PATH` for OTB and GDAL.
3. Applies a runtime fix for `gdal_edit.py`.
4. Translates your exported environment variables into the required Python arguments:
   - `$ORTHO` is passed as `--rgb-ortho`
   - `$RUN_ROOT` is passed as `--out-dir`
   - If `$OVERWRITE` is set to `1`, the `--overwrite` flag is appended.
5. Executes the core Python runner (`level1b_dumb_runner.py`) using these mapped arguments.

The chain runs many steps: preflight, valid mask computation, proxy channel construction, z‑score scaling, scale‑distribution derivation, feature‑range assignment, perturbation generation, candidate response surface evaluation (Step 9a/9b), and finally materialisation of the selected segments with `exactextractr` statistics.

The script prints a final status:

* `level1b_dumb_chain_complete` – all steps finished, and a suitable adjacent scale candidate was found.
* `step9b_non_adjacent_choice_required` – the automated handoff detected a bimodal or multimodal scale distribution; the chain stops and writes a `supported_scale_alternatives.json` that a human can inspect.
* `level1b_dumb_chain_failed` – an error occurred (see the logged `error` field in the chain report).


### 4.4 Outputs

Inside `--out-dir` a `level1b_dumb_chain_report.json` summarises the run. The heavy lifting artefacts reside in `level1b/`:

| Subdirectory / File | Content |
| --- | --- |
| `preflight/reports/preflight.json` | Pre‑flight validation report, OTB app availability, mask contract status. |
| `valid_mask/` | Valid‑pixel mask raster and report. |
| `channels/` | RGB‑to‑proxy multichannel stack (`proxy_stack.tif`). |
| `scaling/` | Z‑score‑scaled feature stack. |
| `scale_distribution/` | Derived scale candidates (JSON). |
| `feature_range/` | Scale candidates enriched with ranger from feature‑space kNN distances. |
| `perturbations/` | JSON of local perturbation candidates. |
| `candidate_response_surface/` | Group and run population summaries (Step 9a). |
| `local_transition_refinement/` | Midpoint probe, handoff JSON (Step 9b). |
| `step10_materialization/decision_evidence/` | Finalist evidence JSON, aggregated group/perturbation tables, figures. |
| `step10_materialization/final_segments/` | The chosen label raster (`selected_labels.tif`) and polygonised segments (`selected_segments.gpkg`). |
| `step10_materialization/segment_stats/` | `selected_segment_exactextractr_stats.csv` and summary JSON. |
| `step10_materialization/quality/` | `ortho_segmentation_quality_info.json` — meta‑information about the evidence package. |

Each step also writes a `step_manifest.json` with its status and artefact locations.

### 4.5 Understanding the Candidate Selection

The chain selects a baseline run from the candidate response surface. A finalist evidence table is built from the top‑ranked scales, and a decision is made based on adjacency and gain‑share heuristics. The chosen candidate scale’s baseline segmentation is vectorised, and `exactextractr` computes per‑segment statistics (count, mean, median, stdev, quantiles) against the scaled feature stack. The quality‑info JSON bundles these statistics with provenance, but it deliberately does not assign a “good” or “bad” label — it is raw evidence for a human reviewer.

## 5. Execution Rules & Troubleshooting

### 5.1 Overwrite Protection

* **Reproducibility analysis (`run-analysis`):** The `--run-dir` must be empty or contain only the prepared `config.yml`/`variants.csv`. If a `manifest.csv` already exists, the command fails. Use `--overwrite` to force reuse of the directory (destroys previous logs).
* **Level‑1b dumb chain:** The script checks for the existence of `out_dir/level1b`; if present, it fails without `--overwrite`.

### 5.2 Resume Behaviour

* `resume-analysis` (subcommand of `metashape-qc`): Reads the existing `manifest.csv` and skips any (variant, replicate) whose status is `ok` or `ok_no_ortho` and whose essential files (project file, launcher log, etc.) still exist. New attempts are appended to the manifest.
* The Level‑1b chain does not have a built‑in resume mechanism; it must be restarted with `--overwrite` (which re‑processes everything) or a fresh `--out-dir`.

### 5.3 Common Problems

| Symptom | Likely Cause & Fix |
| --- | --- |
| `Could not find metashape.sh` | `METASHAPE_DIR` not exported or incorrect. Check with `echo $METASHAPE_DIR`. |
| `metashape-qc: command not found` | The Python virtual environment is not active. Run `source venv/bin/activate`. |
| `Run manifest already exists` | The target `--run-dir` already contains a `manifest.csv`. Switch directories, use `--overwrite`, or run `resume-analysis`. |
| Missing OTB apps during Level‑1b preflight | OTB bin directory not on `PATH`. Add it: `export PATH=/path/to/OTB/bin:$PATH`. |
| R script fails with package not found | Missing R packages. Run `Rscript -e 'install.packages(c(...))'` as described. |
| `ModuleNotFoundError: matplotlib` in Level‑1b chain | `pip install matplotlib`. |
| Level‑1b chain stops with `step9b_non_adjacent_choice_required` | The scale distribution is multimodal; inspect `level1b/local_transition_refinement/supported_scale_alternatives.json`. Re‑run the chain with a sub‑selected ortho or manually pick a scale window. |
| Mixed raster resolutions error in evaluation | The orthomosaics in the manifest have different pixel sizes. Rerun the pipeline without mixing orthoRes or evaluate each resolution stratum separately. |
| No usable `ortho_file` rows found in manifest | All rows in `manifest.csv` have status `failed` or missing ortho files. Check logs in each run’s `launcher.log`. |

For any other error, inspect the relevant log files: `launcher.log` for Metashape runs, the chain report JSON for Level‑1b failures, and the `step_manifest.json` files for per‑step diagnostics.
